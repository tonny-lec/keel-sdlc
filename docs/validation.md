# 検証範囲と限界

## 実行する検証

```bash
make check
```

標準ライブラリのunittestを使う。テスト環境のためだけに外部サービスやAPIキーを要求しない。検査している振る舞いは以下。

| 分野 | 検査する失敗と契約 |
|---|---|
| 入力 | 不明なフィールド／ID、重複、循環、型の混同、NaN、非UTF-8、危険なパス |
| 計画 | ランダム生成DAG、循環を加えた拒否、1,000スライスの直列計画、要求とチェックの対応 |
| 工程 | 一段ずつの遷移、ゲート未達時の無変更、契約変更と巻戻し、再開時の世代競合 |
| 不確実性 | 未決定の停止、低影響の期限付き受容、高影響の受容拒否、反証、技術証拠と要求確認の区別 |
| 証拠 | 古い成功に続く失敗、期限切れ、未来時刻、内容・実行ビット・設定・環境・成果物・ログの変更 |
| 実行 | タイムアウト、stdoutを閉じた処理、出力洪水、子プロセス、欠落した実行ファイル、実行中の入力変更 |
| 予算 | 試行数、全体回数、全体時間、sync後も維持する消費、クラッシュ時の予約消費 |
| 競合と復旧 | 別変更を含む同時実行の排他、二書き手の一勝者、更新途中の例外、孤立した実行の回収 |
| 永続化 | 履歴の再生、投影の破損検出、履歴の破損検出、未知のDBバージョン、バックアップの一致 |
| 引き渡し | パケット改変、再解釈による失効、証拠の差し替え、配置失敗、冪等な再送、観測時刻、振り返り |
| CLI | 実際のモジュール起動、JSON出力、終了コード、上書き防止、文脈の出力 |

さらにデモは、既知の不具合を含む実装を実際にテストし、修正したファイルをローカルの別ディレクトリへ配置して観測する。テスト内で制御境界を検証するために使用するモックと、デモが実行する実際の処理を区別している。

JSON Schemaは`schema.py`の定義から生成する。`scripts/check_schemas.py`で同一性を確認する。参照整合性、DAG、パス、有効期限の関係などは実行時に追加検証する。

## 保証しない範囲

- 自然文の要求が適切か、チェックが十分か、レビューが正しいかという意味上の妥当性。
- レビュー担当の身元、承認権限、署名、外部配置記録の真実性。
- 実行コードの悪意に対するOS隔離、メモリ・CPU・ネットワーク使用量の上限。
- 外部データ、サービス、システムライブラリ、インストール済み全パッケージの完全な指紋。
- 非協調的な書込みに対するファイルシステム全体の原子的スナップショット、実行前後で変更を戻すABA操作の完全検出。
- DB全体を再生成できる主体への改ざん防止、末尾削除を外部の基準なしで検出すること。
- 外部副作用を含む処理のexactly-once実行、自動的なデータ復旧、常駐監視。
- 大規模分散ワーカー、共有ネットワークFSでのSQLite運用、Windowsネイティブのプロセス監督。
- GitHub CIで未実行のPythonバージョンやmacOSでの動作実績。

依存ロック、生成器、ビルド設定をソース範囲に含め、必要ならコンテナイメージや外部データの識別子を契約と調査証拠へ記録する。検証対象を変更不可にして実行し、成果物ハッシュを配置先で照合すると、外部への引き渡しの再現性を高められる。

## 判断の基準

高いテスト数だけで品質を判断しない。重要な条件を壊したときにテストが失敗すること、実行できなかったものを成功としないこと、失敗後に理由と次の操作が残ることを重視する。新しい不具合を修正するときは、その不具合を再現する回帰テストを追加し、関係する範囲で検証する。

v0.1.0はローカルの決定的な制御層として完成した最初の実装である。本番の承認・隔離・署名・配置・常時監視は、導入先の実行基盤と接続して検証する。
