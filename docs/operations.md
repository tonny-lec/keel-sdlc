# 運用・復旧・CI連携

## 信頼する実行設定

`.sdlc/config.json`のチェックは、担当者が確認したコマンドの登録簿である。例：

```json
{
  "argv": ["python3", "-m", "unittest", "discover", "-s", "tests", "-t", ".", "-v"],
  "kind": "test",
  "timeout_seconds": 120,
  "cwd": ".",
  "env": {}
}
```

`argv`はそのまま実行し、shell展開を行わない。必要なパイプや複合処理は、レビュー可能なスクリプトへまとめる。外部デプロイを通常の検証チェックに混ぜると、タイムアウト時に部分実行の副作用が残り得るため、リリース基盤の明示的な操作として分離する。

既定で環境変数は最小限の許可リストだけを引き継ぐ。必要な値は`env_allowlist`またはチェックの`env`で明示する。認証情報をargv、契約、レビュー、ログへ入れない。ログには出力された内容がそのまま残るため、機密を含む可能性があるログを公開する前には内容を確認する。

このランナーはPOSIXのプロセスグループ、時間制限、出力上限を提供する。コードのファイルアクセス・ネットワーク・CPU・メモリを隔離する機能は持たない。信頼できない変更を評価するときは、秘密を渡さない使い捨ての隔離環境にKEELと対象コードを置く。通常の子プロセスは停止するが、意図的に別セッションへ逃げるプロセスまで封じるOS境界にはしない。

## 実行結果の読み方

| status | 意味と次の操作 |
|---|---|
| pass | 正常終了。内容の関連性とゲート上の鮮度を確認する |
| fail | 非0終了。ログと原因を調べる |
| timeout | 壁時計の上限超過。停止後の状態を確認して実験を見直す |
| output_limit | 出力上限超過。ログを無制限に増やさず、必要な診断を絞る |
| interrupted | 操作者の割り込みを捕捉して終了。成功証拠にはならない |
| error | 実行ファイル、作業ディレクトリ、監督処理などのエラー |
| invalidated | 実行前後で入力が違う／同一性を確認できない。安定した入力で再検証する |
| running | 実行予約が残っている。生存する処理を先に確認する |
| abandoned | 操作者が停止確認した未完了試行。予約予算を保持する |

`run`は自動再試行をしない。応答を失った際は`history`と`status`を読み直す。世代番号を付けた同じ更新を再送すれば、実行済みの操作を古い世代から繰り返すことを防げる。

## クラッシュ後の復旧

```bash
keel doctor
keel status feature --json
keel history feature --json
```

`running`が残っていれば、保存された`owner_pid`、`child_pid`、ログ、OSのプロセスツリーを調べる。親の強制終了と子PIDの保存の間にクラッシュする可能性もあるため、子PIDが空であることを「何も実行されなかった」証拠にしない。

実行した可能性のある処理とその副作用を確認し、必要なプロセスを運用者が停止する。その後：

```bash
keel recover feature run-<ID> \
  --reason "対象のプロセスツリーと副作用を確認し、停止を確認した" \
  --confirm-stopped
```

生存している親／子PIDの予約は回収できない。PID再利用で別の処理を誤認した場合も自動で殺さない。外部のプロセス管理と記録を使って原因を確認する。復旧操作は処理を再実行せず、試行をabandonedにして予約時間を消費済みとして残す。exactly-once実行の保証はしない。

## リリース基盤との接続契約

パケットには、契約、判断の回答、残余リスク、入力指紋、成果物のハッシュ、証拠IDとメタデータ、配置・停止・復旧計画が含まれる。証拠本文は`.sdlc/evidence`に保存する。外部へ引き渡す際は必要な本文も一緒に保管する。

外部アダプターの手順：

1. 検証したチェックアウトを変更不可の入力として保持する。
2. 組織が要求する認証済みレビュー、承認、権限、配置先の条件を確認する。
3. `check-packet <id> --file ... --json`が0で終了することを確認する。
4. パケットの`artifacts`と配置する実体のSHA-256が一致することを確認する。
5. 配置先でパケットdigestを冪等性キーとして使い、既存の配置結果を照会できるようにする。
6. 実際の配置結果を次のJSONで出力し、`receipt`へ登録する。

```json
{
  "schema_version": 1,
  "packet_digest": "パケットに記録された64桁のSHA-256",
  "environment": "staging/service-a",
  "deployment_id": "配置先が返したID",
  "outcome": "success",
  "deployed_at": "2026-09-07T12:00:00+09:00",
  "actor": "認証済みCIジョブの識別子"
}
```

上は説明用の例で、実際のdigestと配置日時へ置き換える。失敗時は`outcome: failure`を記録し、拡大を止めて復旧する。配置記録はタイムゾーン付き日時で、パケット作成以降かつ有効期限内である必要がある。

同一入力・同一証拠・同一回答に対する`packet`の再実行は同じパケットを返す。同じ有効な成功配置記録の再登録も、観測開始時刻や世代を変えない。異なる証拠や解釈へ更新した場合は新しいパケットが必要になる。

`actor`の認証、記録の署名、実際の配置先と成果物の同一性はアダプター側で保証する。ローカルJSONの自己申告だけを本番への許可にしない。生成したパケットのハッシュは内容識別子であり、デジタル署名ではない。

## 観測と復旧

`observation_window_seconds`は最低観測時間。登録した配置記録からその時間が経過してから、観測チェックと振り返りを開始する。チェックは対象環境、配置ID、評価区間、対照、失敗率やレイテンシなどの実際の値を確認し、停止条件に達したら非0で終了する設計にする。

KEELが検査するのは時刻と結果の対応であり、自然文の停止条件を自動でメトリクスへ変換しない。サンプルの一瞬の成功で長い評価窓を検証したことにしない。証拠のTTLには、チェック、配置、観測、引き渡しに必要な余裕を設定する。

問題が見つかったら配置範囲の拡大を止め、パケットのrollbackを実行する。コード、設定、データで戻し方が違う場合は別々に手順と検証を用意する。不可逆なデータ変更には、事前の互換性設計・バックアップ復元試験・補償手順を含める。

```bash
keel reopen feature --phase build --reason "配置後に境界値の不具合を検出した"
```

## バックアップと復元

```bash
keel backup .sdlc/backups/state-20260907.db
```

SQLiteのbackup APIで一貫したDBコピーを作る。コピー先の既存ファイルは上書きしない。DBだけでは完全な保管にならないため、同じ作業停止時点の`config.json`、契約、証拠ディレクトリ、対応するソースと成果物も保管する。実行中の予約がない状態で、書き手を止めて保管すると照合しやすい。

復元は新しいディレクトリで行う。すべてのKEELプロセスが停止していることを確認し、DB、設定、契約、証拠を戻す。古い`state.db-wal`／`state.db-shm`を復元先へ混ぜない。`doctor`と`status`を実行し、環境指紋の変更で失効したチェックはその環境でやり直す。破損したDBのハッシュを再計算して正常に見せる修復は行わない。

## このリポジトリのCI

`.github/workflows/ci.yml`は読取権限のジョブで、単体／障害注入テスト、スキーマ差分検査、オフラインデモを実行する。外部の配置先には接続しない。Actionは確認したコミットSHAで固定した。

Python 3.11〜3.14のマトリクスを定義しているが、GitHubへ公開して実行するまでは各バージョンでの成功を主張しない。リリース先に接続する場合は、この検証ジョブと認証済みの配置ジョブを分け、対象組織の権限管理を追加する。
