# 不確実性の扱い

## 依頼を契約に変える

「速く」「安全に」「使いやすく」「最高の」といった表現は意図として保存する。そのまま受け入れ条件にはせず、誰が、どの状況で、何を観測すると成功と判断するかへ具体化する。

例：「検索を速くする」から、対象データ・端末・計測区間・代表クエリを定め、「指定したデータセットでp95が基準以下、既存の検索結果を維持する」という契約へ落とす。閾値の候補と測定方法は提案できるが、既存の合意や計測結果と区別して記録する。

最初に分けるものは、確認済みの事実、要求者の意図、暫定的な仮説、未決定事項である。すべてを質問に変える必要はない。局所的で簡単に戻せる選択は、理由と代替策を記録して進める。

## 台帳

| フィールド | 記録する内容 |
|---|---|
| `kind` | requirement / technical / environment / dependency |
| `question` | 答えが変われば設計や作業が変わる、一つの問い |
| `impact` | 1=局所的な軽微変更、2=限定的手戻り、3=複数箇所の手戻り、4=大きな障害やデータ影響、5=重大な不可逆影響 |
| `confidence` | unknown=根拠なし、partial=一部の根拠、supported=有力な根拠。いずれも解決記録の代わりにはならない |
| `reversibility` | easy / costly / irreversible |
| `blocks` | 答えなしでは入れない工程 |
| `requirements` | 影響する要求ID。空なら全体に影響するものとして扱う |
| `probe` | 複数の解釈や仮説を区別できる、最小の調査・実験 |
| `check` | 実行可能な調査がある場合のチェックID |
| `fallback` | 答えが得られない／仮説が外れた場合の代替策 |
| `effort_minutes` | 調査時間の見積り。自動タイムアウトとは別 |
| `owner` | この問いについて判断を引き受ける役割・担当者 |

## 次に何を調べるか

期限となる工程が早いものを先にし、同じ期限内では次の目安を降順に使う。

```text
exposure = impact × 根拠の不足度 × 戻しにくさ
priority_per_minute = exposure / effort_minutes

根拠の不足度: unknown=3, partial=2, supported=1
戻しにくさ: easy=1, costly=2, irreversible=3
```

これは順序づけのための序数的なヒューリスティックである。校正された確率、経済的な期待値、実験の情報利得を意味しない。異なる単位の影響を精密に比較したという主張にも使わない。実験の関連性、前提の共有範囲、未発見の依存関係は担当者が確認する。

有用な実験には、検証する主張、比較する代替仮説、観測項目、結果の解釈、打切り条件を含める。[調査テンプレート](../templates/research.md)を使える。

## 解決の種類

`answered`は、記録した問いへの回答と根拠がそろった状態である。「仮説が真」と同義にはしない。問いに対する具体的な回答を`--answer`に残す。技術的な検証では、受け入れ条件のテストが通ったことと、全環境で成立するという一般化を区別する。

`accepted`は、低い影響の不確実性を責任者・根拠・代替策・期限付きで引き受ける。影響4以上または不可逆の事項はこの方法で通せない。対象を小さくする、可逆化する、必要な調査をする、のいずれかを選ぶ。

`refuted`は、計画の前提が反証された状態である。契約を修正して`sync`するまで前進ゲートを止める。実験が失敗した場合に終了コードだけを0へ書き換えず、観測を調査記録に残し、問いと実験を修正する。

手書きの回答だけで状態を解決に変更できない。`resolve`には現在の成功した証拠IDが必要で、指定されたprobeがあればそのチェックから得た最新の結果を使う。矛盾する新しい観測が出たら、該当する回答を`refuted`に更新する。自然文同士の矛盾の自動判定は行わない。

## 行き詰まったとき

| 状況 | 進め方 |
|---|---|
| ユーザーの好みだけが未決定 | 可逆な既定値を提案し、影響しない作業を進める |
| 破壊的移行の要件が不明 | 移行の実行前に止め、読取調査・バックアップ検証・移行案の比較を進める |
| 外部仕様が不明 | 一次資料、実際のレスポンス、契約テストを根拠にする |
| ローカル実行環境が壊れている | 製品の失敗と区別し、環境を復元して同じ検証を実行する |
| チェックが不安定 | 成功だけを選ばず、最新の失敗を保持して原因と再現条件を調べる |
| 予算を使い切った | 失敗仮説を整理し、範囲縮小・代替案・明示的な予算変更を検討する |
| 依頼が変更された | 既存の証拠を現在の合意と取り違えず、契約を修正してsyncする |

`next`は未解決事項が直接影響しない作業と、依存先の現在のチェック結果を示す。候補に現れたこと自体は着手の権限や設計上の独立性の証明ではない。共有状態や副作用がないかも確認する。
